● Task 001 设计方案：归档感知的端到端审计（只读阶段）

  ▎ 本轮没有修改任何项目文件。验证实验只在系统临时目录中运行，跑完已清理。

  0. 结论摘要

  - 现有两个审计器各管一半，不能简单拼起来用。e2e.reconcile 能逐条比对，但碰到归档前缀就拒绝；retention.audit
    能读归档，但只检查 consumer 里有没有对应的 event_id，而且运行时会写库。
  - 我用实验确认了 4 个风险。最严重的一个：修剪（prune）后，本地审计会从 FAIL 变成
    PASS，因为被隔离（quarantine）的记录跟着一起进了归档。如果新审计直接沿用现有的本地审计结果，就会得出虚假的
    COMPLETE。
  - 方案：新增独立的只读命令 audit-e2e-archive。现有 audit-e2e、e2e.py、S07 适配器和冻结参考代码一行都不改，也不改数据库
    schema。
  - 新增一项关键校验，叫"源锚定"：把归档的每一条记录和不可变源 JSONL 的对应行逐行比对哈希。归档清单里的 SHA
    和归档本身存在同一个生产者库里，自己证明自己，不能作为独立证据。

  2. 现状分析

  2.1 归档段 schema（retention.py）

  - 清单表 archive_segments：start_file_index（主键）、end_file_index（左闭右开）、record_count、outbox_count、archive_p
    ath、archive_sha256。另有 meta.archived_records，等于最后一段的 end。
  - gzip 内容：mtime=0、文件名为空、压缩级别 6，所以同样的内容总是生成同样的字节。每行是 canonical(item)+'\n'：
  {id, file_index, raw_sha256, payload, received_ns, outcome, detail,
   [outbox:{lane, seq, raw_sha256, payload, acknowledged:true}]}
  - 修剪时会删除（retention.py:162-166）：raw_journal、disposition、outbox、delivery 四张表里对应的行。delivery 这一行的
    ACK 回执没有写进归档，归档里只剩归档器自己写的 acknowledged:true。

  2.3 路径语义

  archive_path 存的是修剪当时解析出的绝对路径（retention.py:168），旧审计直接按这个路径打开（retention.py:198）。目录一
  旦移动或复制就会出问题：路径失效；更糟的是，如果复制后原目录还在，审计副本时会去读原目录里的归档，副本自己缺的段就被掩
  盖了。文件名是确定的：archives/<alias>/raw_{start:012d}_{end:012d}.jsonl.gz。

  注意：registry 里的源路径也是绝对路径，v0.2 的本地审计要求源文件就在原登记位置。所以"整棵目录迁移到另一台机器"在 v0.2
  本来就不支持，本任务不解决这一点。

  2.4 Consumer effects 表

  event_id 是主键，另有 lane、seq、epoch、payload_sha256、payload（canonical 文本），以及 UNIQUE(lane,seq,epoch) 约束。

  4. 设计

  4.1 接口与兼容性（建议，待确认 D1）

  - 新增模块 ftdi_core/archive_e2e.py，提供 reconcile_archive_aware(root, consumer_db, *, report=True) -> dict。
  - 新增 CLI 子命令 audit-e2e-archive --outdir --consumer-db。退出码沿用现有约定：0 = COMPLETE；2 = PENDING / RETRY /
    INCONSISTENT；3 = 前置条件失败即闭锁（fail-closed）。
  - 以下保持不变：audit-e2e、e2e.reconcile、lab-e2e、现有测试 test_archived_prefix_requires_archive_aware_audit。
  - 报告写入新文件 END_TO_END_ARCHIVE_AUDIT.json，schema 为 FTDI-Core-E2E-Archive-Audit-v1，先写临时文件再
    os.replace，不覆盖旧报告。

  4.2 信任锚

  1. 不可变源文件，以及登记在 registry 和 meta 中的源 SHA，作为主锚点。
  2. consumer effects 作为独立证据，要求身份和负载完全一致。
  3. 清单 SHA 和 acknowledged:true 只算生产者自己的声明，不当作独立证据，ADR 中会写明。

  4.3 算法（每条泳道独立处理，只读）

  1. 前置条件（失败返回退出码 3）：registry 可读；consumer 库存在，且不是任何一条泳道的生产者库；各泳道库存在。
  2. 本地审计：原样调用现有 local_audit，保持与 v0.2 一致。但它看不到已归档的处置记录，由第 4 步补上。
  3. 识别清单：要求 meta.schema == 'FTDI-S07-004.1-v1'，archived_records
     是合法的非负整数，清单表的列集合与预期完全一致；各段必须无缝拼接覆盖 [0, archived_records)，每段满足 end == start +
     record_count。
  4. 逐段校验：
     - 只打开根目录内的规范路径；存储路径的文件名必须和规范文件名一致。
     - 整个文件一次读进内存，先算 SHA，再从同一份字节解压，避免"校验完再读"之间被替换。设单段大小上限。
     - 解压、编码、JSON 解析的任何异常（包括 CLI 没有捕获的 EOFError、zlib.error）都转换成问题码，不抛出。
     - 逐条检查：
       - 每一行必须正好是标准化 JSON，字段集合不多不少，类型正确；
       - file_index 连续，id 严格递增，raw_sha256 与 payload 一致；
       - outcome 必须属于已知集合；有 outbox 当且仅当 outcome == ORDERED_PUBLISHED；
       - acknowledged is True；
       - outbox 的 lane 等于登记的 scope，source_seq 与 seq 一致，payload 是标准化文本且哈希匹配；
       - 原始记录与 outbox 绑定：canonical(json.loads(raw)) == outbox.payload；
       - 每段的记录数和 outbox 数与清单一致。
  5. 源锚定：顺序读一遍源文件，同时重新计算整文件 SHA（防止审计过程中源被改）。
     - 第 i 行（i < archived_records）必须等于归档第 i 条记录；
     - archived_records 到 next_file_index 之间的行必须等于驻留 raw_journal 中对应 file_index 的行；
     - 驻留部分的 file_index 必须正好覆盖 [archived_records, next_file_index)，且驻留行的最小 id 大于归档中的最大 id。
  6. 预期账本：在系统临时目录中建一个临时 SQLite（不放在 run 根目录下，用完显式 close 再删），只存身份和哈希，主键为
     (lane,seq,epoch)。归档事件和驻留 outbox 都写入。主键冲突记为 PRODUCER_DUPLICATE_IDENTITY。每条泳道合并后的 seq
     必须连续，且结束于 lanes.next_seq - 1。
  7. 归并比对：账本按 lane,seq,epoch 排序，与 consumer 表做归并连接。驻留行的处理逻辑与 v0.2 完全相同。归档行没有对应
     effect 时记为 ARCHIVED_ACK_WITHOUT_CONSUMER_EFFECT，永远不会被归为 PENDING 或 RETRY。

  4.4 判定规则

  - INCONSISTENT：本地审计失败；或出现任一致命问题码（归档、源锚定、重复、缺口、隔离记录、孤儿、内容冲突、伪造 ACK）。
  - RETRY_REQUIRED：只可能来自驻留部分（consumer 已提交，生产者未 ACK）。
  - PENDING_DELIVERY：只可能来自驻留部分的未投递事件。
  - COMPLETE 兜底不变量：即使前面的判定都通过，下面任何一条不满足，都改判为 INTERNAL_INVARIANT_VIOLATION：
    - 账本条数 == 匹配数 == consumer effect 条数；
    - 已验证的归档事件数 == 各段 outbox_count 之和；
    - 每条泳道：归档数 + 驻留数 == next_file_index == 源文件行数；
    - 按序 event_id 的摘要，账本侧与 consumer 侧相等。

  7. 验收标准

  1. Core 测试由 65 个增加到约 97 个，全部通过；S07 的 45 个测试全部通过；两套都在 -W error::ResourceWarning
     下运行，并在本机 Windows 上实际执行。
  2. 第 6 节中每个损坏夹具都不会得到 COMPLETE，并且命中预期的问题码。
  3. 现有 audit-e2e 和 reconcile 的行为与输出完全不变（以现有测试为证）。
  4. 以测试证明审计前后没有任何证据字节或 schema 发生变化。
  5. 以测试证明：源中有未解决缺口，或归档证据无法验证时，COMPLETE 不可能出现。
  6. 交付中文变更说明：改动文件、确切的测试命令和计数、对事件完整性的影响、残余风险、回滚方法。

  8. 残余风险与局限（写进 ADR 和报告的 limits）

  - 有完整写权限的攻击者：如果能同时改写源文件、registry、生产者库、归档和 consumer
    库，就可以伪造一切。本审计能发现损坏、程序缺陷和局部篡改，没有签名或 WORM 级别的保证。
  - 跨库快照不是原子的：local_audit 和只读快照是两次独立读取。审计必须在维护窗口内进行，期间不能有 prune 或
    publish；我会交叉比对两次读到的计数，不一致就判 INCONSISTENT。
  - 归档的 ACK 只是归档器的声明，因为 delivery 行在修剪时已被删除。归档事件能否判为 COMPLETE，主要取决于 consumer
    中有完全匹配的 effect。
  - 首个观测 ID 之前的前缀不在验证范围内（UNVERIFIED_PREFIX）。COMPLETE 只表示所提供区间内的本地证据链是完整的。
  - 性能：554,441 条全量数据的规模没有测过（源 ZIP
    不在包内），需要你用真实数据验证。设计上是流式处理，内存有界，单段不超过 2 万条。
  - 只读打开 WAL 库依赖 -shm 文件；这和 v0.2 现有行为一致。
